# USB Reverse Engineering

This directory contains some of the tools and analysis results from USB protocol analysis 
on traces captured with the OpenVizsla USB capture device.

All starts with low Level USB protocol traces captured with OpenVizsla (ovctl.py sniff hs). These are basis / truth for further analysis.

## Scripts

- parse_midi_out_capture.py  -- this a purpose specific script to analyse and confirm how the midi out bytes are encapsulated in the audio out frames.

- parse_openvisla.py -- a script that parses the low-level usb wire protocol, and presents these as usb transactions. This remove all the noise from the POLL/NAK etc. low-level handshake of the USB protocol

- reduce_transactions.py -- a script to reduce the parsed transactions as generated by parse_openvizsla.py by removing and truncating certain transfers, specifically the repetative audio (and midi) data transfers. Objective is to end up with a much more compact file showing the relevant transactions for eg. initialization or a rate-change.

- extract_events.py -- folds the EP0 transactions into whole control transfers, groups them into *events* (an initialization or a rate change), and times them. Timestamps are normalized to the start of each event so that captures taken on different machines minutes apart can be diffed directly.

## The pipeline

```
ovctl.py sniff hs   ->   parse_openvizsla.py   ->   reduce_transactions.py   ->   extract_events.py
   raw wire              USB transactions           compact, diffable            timed control plane
   50 MB - 2.25 GB       ~20-50% of raw             ~40 KB                       ~200 lines
```

All three scripts stream, and all accept `-` for stdin/stdout, so the
intermediates never have to be written -- which matters, since the parse of
the largest capture is 1.2 GB on its own:

```sh
python3 parse_openvizsla.py capture_win_power-on_samplerate.txt - \
    | python3 extract_events.py - --format summary
```

Written to files instead, the usual sequence is:

```sh
python3 parse_openvizsla.py capture.txt              # -> capture_parsed.txt
python3 reduce_transactions.py capture_parsed.txt    # -> capture_parsed_reduced.txt
python3 extract_events.py capture_parsed.txt -o capture_events.txt
```

### reduce_transactions.py

Collapses runs of bulk audio packets to the first and last three, with an
elision marker recording how many were dropped, over what span, and per
endpoint. Payloads are truncated to a head and a **tail** slice -- the tail is
not optional, because the MIDI OUT byte (offset 480) and the sync byte
(offset 481) of a playback packet live there.

| Option | Why |
|---|---|
| `--stream-ep 5,6` (default) | collapse audio only; MIDI IN on EP 0x83 stays visible |
| `--stream-ep all` | collapse everything but EP0 -- the mode for control-plane work. 371 MB in, 39 KB out |
| `--start` / `--end` | restrict to a window, in capture seconds |
| `--head-bytes` / `--tail-bytes` | payload truncation, default 16 and 32 |

It warns on stderr if the timestamps ever go backwards. A capture that dropped
packets cannot support any timing conclusion, and that has to be caught before
the analysis, not after.

### extract_events.py

`--format summary` gives one line per event; `--format detail` gives one line
per control transfer with the gap from the previous one, the transfer's own
duration, and the number of bulk packets that flowed in between. Events are
split on an idle gap on EP0 (`--event-gap`, default 250 ms).

The `stream` column is there to separate two hypotheses that look identical in
a timing column alone: whether the device needs *N packets* of stream or *T
milliseconds* before it will accept the next control transfer.

Note that `--event-gap` sits near a real boundary in the Windows captures: the
trailing `CLEAR_FEATURE` pair follows `SET_STATUS` by between 250 ms and
900 ms, so it attaches to the preceding event in some captures and splits off
in others. Raising the default does not resolve it. This changes reported
event spans only.

**A caveat that matters for timing work:** `parse_openvizsla.py` discards NAK
and STALL transactions as polling noise. That is right for glitch hunting, but
it means an idle window and a window full of rejected transfers are
indistinguishable downstream. Before concluding that a gap is the host
*waiting*, check the raw trace for that interval -- see
`init_timing_comparison.md` for a worked example.
